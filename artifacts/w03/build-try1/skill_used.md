# 青禾指标构建方法

本方法只写怎样查证、转换和处理缺口。客户的状态值、金额构成、日期归属、卡产品范围、资格和端点规则一律从输入的业务模型和材料中取得，本方法不提供任何客户事实。

## 一、目标与输入

1. 按输入 `targets` 的 ID 逐项建立处理清单，不新增、不改名、不合并、不遗漏。名称相近的目标（例如“订单数”与“有效订单数”、“购买会员数”与“月内购买会员数”）分别处理，各自找定义。
2. 各输入的职责：
   - `materials` 中的报表说明、财务邮件、运营周报、统计确认邮件：提供每个目标的统计对象、计入与排除条件、时间归属、分子分母、零分母处理和查询限制。
   - `materials` 中的数据字典：只提供物理列名、类型、单位和表间关联；字段存在不等于业务上应计入，字典明确说“不裁定”的内容不能当规则用。
   - `business_model`：提供业务对象、角色、关系、粒度、已答复规则及其状态（例如“待书面确认”“未决”），以及数据范围限制。
   - `access_tables`：接入层四张表的实际列名与类型；`time_spine` 由框架提供。
   - `dimension_targets`：本次要覆盖的 12 项查询维度。
3. 对每个目标先判断属于哪种情况：（a）材料给了定义且字段齐全；（b）材料给了定义但某个条件的业务规则在任何输入中都找不到；（c）材料之间说法冲突且没有已确认的适用范围；（d）字典缺少所需字段。只有（a）可以定义；（b）（c）（d）进入第五段处理。区分“材料没给定义”与“字典没给字段”，不能凭指标名称、字段名或行业常识补口径。
4. 业务模型中标为“已口头答复，待……书面确认”的规则，可以作为本期定义依据，但必须在 catalog 的 constraints 中写明该状态，不能写成“客户已确认”。业务模型中标为“未决”“不掌握”“待核实”的事项不是规则，不能用于定义。

## 二、候选及依据

1. 为每个目标整理七项事实，每项都要在输入中找到依据：统计对象与粒度（订单、账户、门店、账户×月等）；统计时间及归属日期；计入与排除条件；金额或数量构成（计入项与扣减项）；聚合方式（求和、计数、去重计数、比率）；单位；查询限制（是否只支持完整自然月、是否只支持全渠道全门店、多月是否须按月分别列出）。
2. 一个目标的定义散在多份材料时（例如报表说明给出分子，财务邮件给出“有效”的含义），把它们一起作为依据，各自引用。同一词在不同材料中范围不同时，按材料写明的适用范围选择；没有写明适用范围的不同说法，按冲突处理。
3. catalog 的 `sources` 中每条 `file` 必须是输入中真实存在的文件名（业务模型用 `business_model_filename`），`quote` 必须是该文件中的**连续原文**，逐字复制，不改标点、不合并两段、不加省略号、不把自己的解释写进引文。引文应能直接支持对应定义；只引用标题或无关句子不算依据。比率指标除了引用比率本身的原文，还要能从依赖指标追到分子分母的定义。
4. `business_model_usage` 只记录实际采用的业务模型连续原句，并在 `used_for` 中写明用于哪个语义模型、维度、派生模型或指标。

## 三、字段与计算转换

1. 先确定表达式作用的行（第六段决定的模型和粒度），再把已核实条件映射到字典中的列。列名逐字使用 `access_tables` 中的标识，展示用中文与物理列名分开。
2. 计入与排除条件写进 measure 表达式：不满足条件的行在求和时取 0、在去重计数时取 NULL。状态值、金额比较方式（大于、等于、小于）严格按材料原文，不能把“大于零”写成“大于等于零”，也不能把“等于实付”写成“大于等于实付”。
3. 金额类指标逐项核对计入项与扣减项是否齐全；底层单位按字典（例如整数分）保持，不在表达式中换算成元。
4. 聚合方式与统计对象一致：
   - 统计对象是事实行本身（如订单）且一行就是一个对象：对条件取 1／0 后 `sum`。
   - 统计对象是事实行关联的另一个对象（如账户、门店），同一对象可能出现在多行：用 `count_distinct`，表达式在满足条件时返回该对象的键，否则返回 NULL。
   - 统计对象是“对象×期间”或需要先跨行累计、排序、判断资格：交第六段生成派生模型，在派生模型的粒度上计数或求和。
5. 比率用 `ratio` 类型，numerator、denominator 引用已定义的指标 ID。零分母未定义，不改成 0；不在 measure 中预先相除。
6. 空值：不能把未知或未定义改成 0。只有材料说明某种情况计为 0 时才取 0。

## 四、依赖与输出协议

1. 只返回一个 JSON 对象，顶层恰好包含 `semantic_models`、`metrics`、`catalog`、`model_sql`、`grain_keys`、`unresolved`、`business_model_usage`。不返回 Markdown、YAML、代码围栏或解释文字。形状按输入 `contract`，格式按 `native_format`（dbt semantic_models/measures 旧写法，MetricFlow 0.213）。
2. 每个已定义目标在 `metrics` 中恰有一项，`name` 等于目标 ID；simple 指标用 `type_params.measure` 引用 measure；ratio 指标的分子分母引用本次输出中已定义的指标 ID。比率依赖的指标若不在本批 targets 中，该比率列入 unresolved，不能引用不存在的指标。measure 名称全局唯一，建议用“目标 ID＋_measure”或含义明确的名称。
3. `catalog` 只收录已定义目标，每项给出 `id`、`name`（与 targets 中文名一致）、`aliases`（客户材料中出现的别称，没有则空数组）、`unit`、`constraints`、`sources`、`query_policy`。
   - `unit` 按量纲选择：订单、账户、门店、件等计数用 `count`；金额用 `cents`；无量纲比例用 `ratio`；金额÷订单用 `cents_per_order`；金额÷账户用 `cents_per_member`；订单÷账户用 `orders_per_member`；件÷订单用 `items_per_order`。分子分母量纲决定单位，不能因为结果是小数就填 `ratio`。
   - `constraints` 写查询和解释时必须提醒的限制：归属日期、是否含取消单、零分母未定义、规则状态（如“运营口头答复，待书面确认”）、数据限制（如“按账户当前等级，不是注册当时等级”、某字段含义待核实、不作考核依据等），每条都要能在输入中找到依据。
   - `query_policy.full_month_only`：材料明确要求某指标只支持完整自然月（或只支持整月、全渠道、全门店）时为 true，否则为 false。限制必须写进 query_policy，不能只写在 description。
4. `model_sql` 只放第六段生成的派生模型，键为合法小写模型名，值以 SELECT 或 WITH 开头；不需要派生模型时为空对象。
5. 输出前自查：targets 中每个 ID 恰好出现在 metrics 或 unresolved 之一；catalog 与 metrics 的 ID 集合一致；所有 measure、指标依赖、ref 的模型都在本次输出内闭合。

## 五、未决、冲突与修订

1. 出现第一段第 3 条的（b）（c）（d）情况时，把目标以 `metric_id` 列入 `unresolved`，不进入 metrics 和 catalog。`missing_facts` 写具体缺什么（例如“某日期字段落在判断日当天是否计入的规则”），`reason` 写影响哪部分计算，以及业务模型或材料中记载的负责核实的角色和要问的具体问题；输入中没有记载负责人时写“请项目对接人确定负责人”，不编人名。
2. **资格与有效期**：判断某对象在某时点是否具备资格时，开始日当天、结束日当天、提前终止日当天是否计入，空的终止日期表示什么，多条记录重叠怎样处理，每一项都必须在输入中找到规则。输入只覆盖其中一部分时，依赖未覆盖部分的全部目标列入 unresolved，并逐项写明哪个端点缺规则。不能用数据库比较习惯、字段名含义或“常见做法”选择 `<`、`<=`、`>` 或 `>=`；不能为了让目标可执行而先写一个暂定比较。
3. 冲突：两份输入在同一适用范围内说法不同，且输入中没有写明哪一个取代另一个，列入 unresolved 并写出两处原文所在文件。材料时间先后、措辞强弱本身不构成取代依据。
4. 维度：`dimension_targets` 中某项缺少已确认的关系或属性时，以 `dimension_id`、`missing_facts`、`reason` 列入 unresolved；关系已在字典或业务模型中写明的，不能为省事列未决。
5. 每个目标只能出现在已定义或未决其中一边。不要把自己的推断、构建检查结果或可编译性写成客户事实。

## 六、语义模型与派生模型

1. **先声明一行代表什么**。为每个语义模型确定：一行代表的业务对象或“对象×期间”、主实体、外键实体、维度、默认统计时间。模型按业务对象和角色组织，不机械地一张表一个模型。
2. **对象与角色**：
   - 订单模型：一行一笔订单，主实体为订单键；外键关联会员账户与订单上的门店；渠道、状态等作为局部维度；统计时间用订单日期列。
   - 账户模型：一行一个账户，主实体为账户键；账户上的门店是另一种角色（归属门店），与订单上的门店分开命名实体；等级等账户属性作为局部维度；有注册类指标时以注册日期作为统计时间。
   - 门店：同一物理门店表在不同关系中承担不同角色时，为每个角色各建一个语义模型（引用同一 ref），主实体名分别对应角色，维度用相同的局部名（如 region、store_name）。
   - 查询 ID `实体名__属性名` 由 MetricFlow 组合：实体名必须与 `dimension_targets` 的前缀一致（如 `store`、`home_store`、`member`、`order`），`dimensions[].name` 只写局部名。
3. **需要派生模型的三类规则**，先按业务模型和材料核实规则，再生成 SQL：
   - **排序**（如首单、后续订单）：先在材料要求的历史范围（例如全部数据覆盖期，而非查询窗口）内，按材料规定的对象、计入条件、排序字段和平手规则产生序号，得到一行一笔参与排序的记录；查询窗口只在其后按记录日期筛选，不能改变序号。
   - **按期汇总**（如对象在自然月内的次数或金额）：先聚合到“对象×期间”一行，期间起始日作为该模型的时间维度（用非保留列名，如 `month_start`），再在此粒度上按条件计数或求和。跨期间人数不能由各期相加得到，相关指标设 `full_month_only`。
   - **资格判断**（如期末是否具备某资格）：先确定判断对象和判断时点，把多条资格记录按输入规则收敛为“对象×期间”一行的布尔结果，再与同粒度的期间汇总结果按对象键和期间关联。不能把资格明细直接连到订单或期间表上，以免一对多放大人数和金额。规则不全时按第五段第 2 条处理。
4. **派生模型的粒度与实体**：派生模型表示与原表不同的行集合或粒度时，使用自己独立的主实体名（例如 `member_month`、`ranked_order`），并保留需要的外键实体（如 `member`），不复制原表的主实体与时间维度配对。若派生模型需要支持与原表相同的维度查询（如按门店、渠道拆分），只在该派生模型的一行确实只属于一个该维度取值时带上相应外键或局部维度；否则不带，让该维度对此指标不可查询。
5. **grain_keys**：每个语义模型都要声明，值是该模型实际存在的列名列表；单键给主键列，组合粒度逐列列出（如 `["member_id", "month_start"]`），不填 SQL 表达式、不用会吞掉空值的拼接键代替。若派生模型为连接另造一个组合键作为主实体，grain_keys 仍逐列列出真实组成列。
6. **关联检查**：外键实体必须指向同一业务对象且在目标模型中唯一、非空的主实体；外键列有空值时先核实业务是否允许，不能为了通过检查填默认值。一对多关系先在“一”的粒度上汇总或用 EXISTS 判断，再关联。
7. **派生 SQL 规则**：只用 SELECT／WITH，引用接入模型和其他派生模型时用 `{{ ref('模型名') }}`；不使用文件、网络、DDL、DML；派生模型名为合法小写名，不与 members、stores、cards、orders、time_spine 重名。日期运算使用 DuckDB 语法。
8. **原生命名限制**：`metric_time` 以及 `day`、`week`、`month`、`quarter`、`year` 等时间粒度词不能作实体或维度名；时间维度用字典中的日期列或派生表自己的非保留日期列名，并在 `defaults.agg_time_dimension` 引用。有 dimensions 的模型必须有 primary 实体。一个实体名只能有一个 primary 目标；同一主实体与同一维度名的配对在所有模型中唯一。输出前逐项检查这些约束，不依赖程序替换名称。
9. **维度覆盖**：逐项核对 `dimension_targets`，确认每项能从至少一个指标沿实际实体关系查询到，或已按第五段列入未决。维度全覆盖不意味着每个指标都要支持全部维度；指标只支持其模型粒度下真实成立的维度。
